# 2026-09-04 — Roadmap projections must follow verified capability

## Context

By current main, the generic governed-growth substrate had advanced beyond the wording still present in `ROADMAP.md`. The roadmap continued to describe the DSH interaction → selective Experience/governance path as missing even though the repository already contained that path, plus independent governance, same-process context refresh, revision, retirement, consolidation, bounded current cognition, auditable review, and a deterministic real-runtime proof runbook.

## Decision

`ROADMAP.md` is a living projection, not an immutable historical record. When verified repository truth moves ahead of its wording, update the roadmap to describe the current capability and the actual remaining falsifiable gap.

Historical evolution records remain immutable and are not rewritten to make the newer architecture appear inevitable.

For M3/M4 at this point:

- generic Experience capture and selective proposal plumbing are implemented;
- learn/revise/forget/consolidate are governed current-cognition operations, not automatic transcript storage;
- current cognition is bounded and remains distinct from historical evidence;
- human review remains an independent mutation boundary;
- the remaining M4/M4.1 acceptance gap is a real DSH TUI/Web interaction → review → persisted mutation → next real model-turn proof;
- Samuel-specific #7 remains Experiment 001 evidence and is not a generic growth dependency.

## Why this matters

A stale roadmap can create false dependencies and cause autonomous development to rebuild capabilities that already exist. Conversely, marking a runtime proof complete because plumbing exists would weaken falsifiability. The roadmap therefore has to distinguish three states explicitly:

1. engineering substrate implemented;
2. automated/integration evidence available;
3. required real-runtime evidence actually observed.

Only the third state may satisfy an acceptance criterion that explicitly requires a real runtime.

## Consequence

Future planning should recompute from current main, open issues, CI, runtime evidence, current docs, and immutable evolution records. Milestone numbering is secondary to the smallest coherent capability gap that remains observable and falsifiable.
